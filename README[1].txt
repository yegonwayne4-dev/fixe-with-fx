FIXE WITH FX — PAID FOREX TRAINING MEMBERSHIP BACKEND (SANDBOX STARTER)
============================================================

WHAT THIS VERSION DOES
- Basic Class: KSh 200 one-time registration. Premium Class: KSh 1,000 one-time access. Premium can be purchased initially or as an upgrade from Basic.
- Server-side account registration and login; passwords are bcrypt-hashed.
- SQLite database for users, sessions and payment attempts.
- Safaricom Daraja M-PESA Express (STK Push) integration in SANDBOX mode.
- Flutterwave hosted card checkout for Visa/Mastercard in TEST mode (card-only payment options).
- Server-side verification before setting a user's paid_at membership flag.
- Payment history endpoint, basic request rate limits, same-origin checks and secure session cookie settings.
- Demo trading remains simulated; no broker connection, no real trading, no customer trading wallet, and no withdrawals.

IMPORTANT
This is an integration starter, not a live-ready or regulator-approved financial service. The front end is only the customer interface; the server and provider credentials must be deployed on a secure HTTPS host. Do not accept live payments until your business, product classification, payment provider merchant account and any CMA requirements have been confirmed. Do not describe virtual demo profit as cash or allow it to be withdrawn.

REQUIREMENTS
- Node.js 20 or newer
- npm
- Public HTTPS URL for provider callbacks (a localhost URL is not reachable by Safaricom/Flutterwave)
- Sandbox/test credentials from Safaricom Daraja and Flutterwave

INSTALL ON A COMPUTER / HOSTING SERVER
1. Extract this ZIP.
2. Open a terminal in the Fixe_with_FX folder.
3. Run: npm install
4. Copy .env.example to .env.
5. Generate a strong random secret (at least 32 characters) for SESSION_SECRET and a separate random MPESA_CALLBACK_TOKEN and FLW_WEBHOOK_SECRET_HASH.
6. Fill in the sandbox credentials described below.
7. Set PUBLIC_BASE_URL to your public HTTPS deployment/tunnel URL (no trailing slash required).
8. Run: npm start
9. Open the website at http://localhost:3000 for local browsing. Provider callbacks still need the public HTTPS URL to route back to this server.

SAFARICOM DAR AJA SANDBOX SETUP
1. Create/sign in to a developer account at https://developer.safaricom.co.ke/.
2. Create a sandbox app with M-PESA Express / Lipa Na M-PESA Online enabled.
3. Copy the sandbox Consumer Key and Consumer Secret into DARAJA_CONSUMER_KEY and DARAJA_CONSUMER_SECRET.
4. Use the sandbox shortcode and Lipa Na M-PESA passkey shown by Safaricom in DARAJA_SHORTCODE and DARAJA_PASSKEY. The commonly documented sandbox shortcode is 174379; use the values in your own Daraja app documentation.
5. Keep DARAJA_ENV=sandbox. Configure a public HTTPS callback URL using the callback token route generated by the app. Never put credentials in index.html.
6. Sandbox phone-number and simulation requirements are controlled by Safaricom's sandbox environment.

CARD SANDBOX SETUP (FLUTTERWAVE)
1. Create a Flutterwave merchant/developer account and use TEST credentials.
2. Put the TEST secret key in FLW_SECRET_KEY. It is server-only and must never be exposed to the browser.
3. In the Flutterwave dashboard, configure the webhook URL as:
   https://YOUR-DOMAIN/api/flutterwave/webhook
4. Set the webhook secret hash in the dashboard and put the same value in FLW_WEBHOOK_SECRET_HASH.
5. This integration requests card-only checkout (Visa/Mastercard availability is subject to your verified merchant account and Flutterwave settings).
6. The redirect is verified server-side through Flutterwave's transaction verification API. The webhook signature is checked and the transaction is independently verified before membership is activated.

PAYMENT FLOW
- New customer creates an account. They are signed in but remain unpaid.
- They choose Basic (KSh 200) or Premium (KSh 1,000), then pay by M-PESA or card. Premium upgrade is available to Basic members.
- M-PESA: backend requests STK Push. A callback is not blindly trusted; the server queries Daraja for the CheckoutRequestID and checks the callback amount against the selected plan price.
- Card: backend creates a Flutterwave hosted checkout URL. The redirect/webhook is not blindly trusted; the server calls the transaction verification endpoint and checks status, tx_ref, KES currency and the exact amount for the selected plan.
- Only after verification does the server set users.paid_at. The dashboard is then unlocked.
- Duplicate provider notifications do not create duplicate payment rows or duplicate memberships.

ADMIN ACCOUNT (OPTIONAL)
There is no hard-coded administrator account or password. After the database has been initialized once by starting the server, run:
   npm run create-admin
Use a unique email and a strong password of at least 14 characters. The admin endpoint for payment records is GET /api/admin/payments. Do not share admin credentials.

SECURITY / DEPLOYMENT CHECKLIST
- Set NODE_ENV=production, SESSION_SECRET (32+ random chars), and PUBLIC_BASE_URL=https://your-domain.
- Serve only over HTTPS and keep .env out of source control/backups shared publicly.
- Use a managed host with persistent disk for SQLite or migrate to managed PostgreSQL before scaling/multiple server instances.
- Back up data/fixe.sqlite securely; restrict file access.
- Configure firewall, monitoring, dependency updates, privacy notice, terms, refund policy and customer support.
- Never request or store a customer's M-PESA PIN or card number/CVV. Hosted card checkout keeps card entry with the provider.
- Reconcile provider statements to the payments table. Pending payments must be investigated before asking a customer to retry.
- The app currently does not implement production-grade admin UI, email verification, password reset, account deletion, a formal refund workflow, or automated payment reconciliation reports.
- Do not change PAYMENT_MODE or provider environment to live until the relevant merchant onboarding and regulatory checks are complete.
